# ngx_http_waf_module

Реализация модуля. Спецификация целевого продукта — в docs/ (`docs`), этот документ
описывает только устройство кода: выбор языка, границы между слоями и карту файлов.

## Язык

**C11** для модуля, **Go или Rust** для инспекторов и сайдкаров.

Выбор языка модуля определяется не вкусом, а тем, где сосредоточена сложность. Она вся —
внутри nginx: повторный вход в access-фазу через `ngx_http_core_run_phases()`, цепочка
фильтров на фазе ответа, слаб-аллокатор `ngx_shm_zone`, а на этапе 12 — собственный
обработчик апгрейженного соединения взамен `ngx_http_upstream_process_upgraded()`. Всё это
внутренний C-API nginx, и никакой обёртки над ним нет.

Что было рассмотрено и отклонено:

| Вариант | Почему нет |
| --- | --- |
| Rust через `ngx-rust` | Крейт `ngx` 0.5.1 имеет статус WIP, API не стабилизирован, ломающие изменения заявлены авторами. Перечисленные выше места всё равно пришлось бы писать в `unsafe` поверх сгенерированных bindgen привязок: опасность C сохраняется, а инструментарий C теряется. Привязки ломаются от `configure`-флагов и дистрибутивных патчей nginx |
| C++ | Пуловая модель памяти nginx конфликтует с RAII, исключения через границу C-ABI в динамическом модуле — источник трудноуловимых аварий |
| Lua (OpenResty), njs | Нет доступа к shm-зонам, циклу событий и цепочке фильтров на нужном уровне. Стоимость на запрос несовместима с бюджетом в единицы миллисекунд |

Инспекторы — отдельные процессы, общающиеся с модулем только сообщениями. Писать их на C
незачем: там нужны разбор JSON, регулярные выражения и библиотеки, а не работа с пулами.

### Чем платим за C и как это закрывается

Единственное место, куда попадают непроверенные байты, — разбор ответа инспектора. Оно же
и самое опасное: инспектор, способный подставить произвольный заголовок, cookie и код
ответа, — это удалённый редактор трафика.

Из этого следуют правила, обязательные с первого коммита, а не «потом»:

- Разбор JSON — один парсер без аллокаций, работающий по буферу с явной верхней границей
  `waf_reply_max`. Никаких сторонних JSON-библиотек в горячем пути.
- Каждый парсер имеет харнесс в `fuzz/` (libFuzzer + ASan + UBSan): сейчас это JSON,
  ответ инспектора, проводной протокол NATS и RESP; кадрирование WebSocket и gRPC
  появятся вместе с фазой кадров. Прогон -- `docker build -f fuzz/Dockerfile` из
  `nginx/module`, в CI пока не подключён.
- Сборка и прогон функционального набора под ASan и UBSan; отдельный прогон под valgrind.
- Все строки — `ngx_str_t` с явной длиной. `strcpy`, `sprintf` и `strlen` по данным с
  провода запрещены.

## Границы слоёв

```
                     ngx_http_waf_module.c
              (директивы, фазы, фильтры, воркер)
                              |
        +---------------------+---------------------+
        |                     |                     |
      core/                runtime/                bus/
   разбор конфига      горячий путь            транспорт
   волны (цель: wave=; сейчас after=)  машина состояний  (за vtable)
   волны и маски       слоты ожидания
        |                     |                     |
        +----------+----------+----------+----------+
                   |                     |
                codec/                 body/
          сериализация и          драйверы хранения
          валидация канала        (за vtable)
                   |                     |
        +----------+----------+          |
        |                     |          |
     local/                 net/ <-------+
   shm, лимиты,      соединение с внешним
   breaker, датасеты  сервисом: сокет, буферы,
                      переподключение (без протокола)
```

`net/` -- общий скелет двух самописных клиентов, NATS (`bus/`) и Redis (`body/`):
неблокирующее соединение в цикле событий, вечное переподключение по таймеру, входной
буфер со сдвигом разобранного, исходящий буфер с пределом роста. Протокол остаётся у
владельца и приходит колбэками `on_connected` / `on_read` / `on_close`.

Правила, которые эти границы задают:

**`runtime/` не знает, какая шина под ним.** Всё общение — через `ngx_http_waf_bus_t`.
Это не абстракция ради абстракции: пока транспорт выбирался (см. ниже), машина состояний
писалась и отлаживалась независимо от него, и заменить NATS на что-то другое не значит
переписать её снова.

**`bus/` не знает ни про JSON, ни про вердикты.** Транспорт получает байты и отдаёт их в
`ngx_http_waf_bus_dispatch()`. Разбор и валидация ограничений канала — в `codec/`.

**Колбэк транспорта исполняется строго в потоке цикла событий nginx.** Он добирается до
`ngx_http_request_t`; вызов из чужого потока — это гонка и use-after-free одновременно.

**Ничто из `runtime/` не аллоцируется в `r->pool`, если может пережить запрос.** Слот
ожидания — в памяти воркера, состояние клиента шины и его таймеры — в пуле цикла.

## Про транспорт: решение

`docs/roadmap.md` предполагал `nats.c` с `natsOptions_SetEventLoop()`.
Проверка показала, что этого недостаточно: опция убирает только поток чтения сокета, но
каждая асинхронная подписка по-прежнему получает собственный поток доставки, который и
вызывает пользовательский колбэк. Для нас это неприемлемо — колбэк трогает состояние
запроса nginx.

Поэтому написан **собственный клиент поверх `ngx_event`**
(`bus/ngx_http_waf_bus_nats.c`). Текстовый протокол core NATS невелик: `CONNECT`, `PUB`,
`SUB`, `MSG`, `HMSG`, `PING`, `PONG`, `INFO`, `-ERR`. Публикация аудита в JetStream в
режиме fire-and-forget — это обычный `PUB` на subject потока, JS API не нужен. Взамен: ни
одного чужого потока, аллокации из `ngx_pool` и отсутствие внешней зависимости в модуле,
собираемом с `--with-compat`.

Два свойства клиента стоит знать, потому что они неочевидны и оба про корректность:

**Адресация ответа — в reply-to, состояния сопоставления нет.** Ответ уходит на
`<inbox>.<rid>.<ii>`, где `ii` — номер инспектора. Индекс отдельным элементом нужен именно
для `no_responders`: сообщение об отсутствии подписчиков приходит без payload, и понять, о
каком инспекторе речь, можно только по адресу.

**Таймеры клиента объявлены `cancelable`.** Завершающийся воркер выходит, когда не осталось
неотменяемых таймеров, а `ping` перевзводится вечно. Без флага воркер не выходит никогда —
то есть не завершаются ни `reload`, ни остановка, и мастер добивает воркеры по таймауту.

## Ключевые решения в написанном коде

**`rid` кодирует индекс слота и поколение** — `(gen << 24) | index`. Поиск слота это
индексация и одно сравнение, без хеш-таблицы, которую предполагает спецификация. Поздний
ответ на завершённый запрос не находит ничего по несовпадению поколения. Побочный
результат — жёсткая верхняя граница числа запросов в полёте (`waf_max_inflight`), которой
иначе не было бы вовсе.

**Поколения стартуют со случайного значения**, разного в каждом воркере и в каждом
поколении конфигурации. Иначе после `reload` новый воркер выдаёт те же `rid`, что и
завершающийся, и вердикт для чужого запроса совпадает по всем полям.

**Массив ответов выделяется одним куском на всю таблицу**, а не по 64 записи на слот, как
в наброске `ngx_http_waf_slot_t` из execution-model.md. При 4096 слотах разница — десятки
мегабайт на воркер.

**Связь `ctx` → слот рвётся через `ngx_pool_cleanup_add()`**, а не только на штатных путях
завершения: nginx освобождает пул и при обрыве соединения, и при внутреннем редиректе.

**`r->main->count` не инкрементируется.** Для access-фазы nginx не вызывает
`ngx_http_finalize_request()`, декрементировать счётчик будет некому, и запрос не
освободится никогда. Тест на утечку счётчика обязан быть в наборе с самого начала.
Единственное исключение — чтение тела: `ngx_http_read_client_request_body()` инкрементирует
счётчик сам, и компенсировать это обязан вызывающий, поэтому сразу за ним идёт
`ngx_http_finalize_request(r, NGX_DONE)`. Тот же порядок — в `ngx_http_mirror_module`.

**Пассивный инспектор ждут, но его вердикт не применяют.** В целевой модели маска волны —
`mandatory` и `passive` (`mode=` на `waf_inspect`); ждут обоих, гейтит только `mandatory`.
`advisory` снят. Если к дедлайну не хватает лишь пассивных, фаза считается успешной и политика
`waf_deadline` не включается. Семантика режимов — в
`docs/execution-model.md`.
Текущий код ещё держит третью маску `advisory`.

**Ответ, не прошедший проверку, отбрасывается, а не превращается в отказ.** Волна продолжает
ждать инспектора, и решает дедлайн. Иначе прислать мусор было бы выгоднее, чем не отвечать:
битый ответ уводил бы запрос в класс `bus`, у которого другое значение по умолчанию.

## Что локальный слой требует от реализации

**Разметка зоны не зависит от конфигурации.** Число слотов наборов — константа
(`NGX_HTTP_WAF_MAX_DATASETS`), а не число объявленных наборов: после `reload` старые воркеры
продолжают работать в той же зоне со своей разметкой, и любое расхождение в форме означало бы
чтение чужой структуры. Слот находится по имени набора, а не по индексу в конфигурации.

**Набор — неизменяемый снимок, публикуемый одной записью указателя.** Отсюда отказ от радиксного
дерева: дешёвая вставка не нужна, а отсортированный массив диапазонов с массивом максимумов конца
даёт принадлежность двоичным поиском, вчетверо плотнее и обходится проходом по непрерывной памяти.
Дельта означает построение нового набора из действующего целиком.

**Отставленный набор освобождает не тот, кто его заменил.** Читатель поднимает счётчик перед
поиском и опускает после, а прежний набор попадает в массив отставленных и освобождается, когда
счётчик обнулится. Без этого подмена указателя — use-after-free ровно в тот момент, когда в зоне
что-то происходит: воркеров много, и читают они без блокировки.

**Обновление разбирает один воркер.** Сообщение JetStream приходит всем, поэтому применение
начинается с заявки на номер под мьютексом: остальные видят её и отбрасывают сообщение, не разбирая
записи. У заявки есть срок — иначе упавший в середине воркер заблокировал бы номер навсегда.

**Счётчик частоты ищется по подписи правила, а не по маршруту.** Дерево в зоне одно на все правила,
а различает их подпись — хеш от текста ключа, частоты, всплеска и способа счёта, — и она же входит в
ключ узла рядом с хешем значения переменной. Одинаково объявленный лимит на двух маршрутах
оказывается одной корзиной, и это свойство, а не ошибка: иначе объявление того же лимита в двух местах
давало бы вдвое больший пропуск.

**Начисление за волну не подчиняется тому же правилу, что защита запросов.** Проверка запроса
отвергает начисление за пределом всплеска, иначе клиент продлевал бы себе блокировку сам. Волна
наоборот: её цена должна записаться, даже когда корзина уже полна, — иначе накопленное никогда не
превысит всплеск и `count=waves` не сработает ни разу. Сверху долг ограничен секундой частоты сверх
всплеска, чтобы шторм волн стоил ключу секунды блокировки, а не часов.

## Что тело требует от реализации

Модель — в `docs/body-storage.md`. Здесь то, что она означает для кода.

**Тело читается настолько поздно, насколько возможно.** Не в начале access-фазы, а в
`wave_start()` той волны, которая его требует: запрос, заблокированный на нулевой волне по
адресу или заголовку, не приводит ни к чтению тела, ни к обращению к хранилищу. Требование
волны — максимум по `body=` её инспекторов, а содержимое в сообщении получает только тот, кто
его просил: `body=none` видит `null` даже при размещённом теле.

**Колбэк чтения тела вправе быть вызван синхронно.** Тело может быть уже прочитано целиком, и
тогда `ngx_http_read_client_request_body()` вызывает обработчик из своего стека — то есть фазы
проходятся заново изнутри вызова. Отсюда отдельное состояние `ST_READING_BODY`: повторный вход
обязан увидеть «уже читаю», а не начать чтение второй раз. То же и у драйвера: `put()` вправе
позвать `op->handler` изнутри себя (соединение могло оборваться ровно в момент отправки), и
флаги `body_in_put`/`body_settled` отличают этот случай от настоящего асинхронного ответа, в
котором запрос в фазы возвращает сам колбэк.

**Тело собирается в один буфер, а хеш считается одним проходом.** Драйверу без `CAP_STREAMING`
цепочка буферов бесполезна, а SHA-256 всё равно требует полного прохода. Тело в файле читается
здесь же, блокирующим `ngx_read_file()` — неблокирующее чтение файла в цикле событий
потребовало бы пула потоков ([known-issues.md](known-issues.md)).

**Ключ снимается при разрешении вердикта, а не в конце ответа.** Удаление стоит в начале
`dispatch_state()`, куда путь ведёт только из терминального состояния: между волнами тело ещё
нужно, а после вердикта — уже нет. Пул запроса живёт до конца ответа, и у проксируемого запроса
это весь round-trip до апстрима. Cleanup пула при этом тоже зарегистрирован — как страховка от
путей, на которых вердикта нет вовсе: обрыв соединения, внутренняя ошибка.

**Недоступность тела — это состояние с политикой, а не ошибка.** Причина (`oversize`,
`store_error`, `store_unconfigured`) едет инспектору в локаторе, а исход решает
политика `waf_body_limit` или `waf_exception … body`. Политику запоминает тот, кто обнаружил
недоступность: по состоянию превышение размера от отказа хранилища не отличить, и выбор
директивы по нему означал бы применять одну вместо другой.

**Драйвер живёт в цикле событий и только там.** Соединения `redis` принадлежат воркеру, а не
запросу: пул поднимается в `init_worker`, операция ставится в конвейер, ответы разбираются по
порядку отправки. Запись операции при этом выделяется из пула цикла, а не запроса, и на пул
запроса ставится cleanup, обнуляющий ссылку: иначе оборванный запрос уносит с собой память, на
которую смотрит ответ, ещё летящий от Redis. Отбросить ответ можно, порвать конвейер — нет.

## Что скоринг требует от реализации

Модель — в `docs/verdict-protocol.md`. Здесь только то,
что она означает для кода.

**Резолюция перестаёт быть максимумом по вердиктам.** Числовой порядок
`allow < score < redirect < deny` в `ngx_http_waf_verdict_e` сохраняется и по-прежнему даёт
«наивысшее явное требование» одним сравнением, но итог им больше не определяется:
между `deny` и `redirect` вклинивается проверка порога, а `score` сам по себе исхода не
задаёт вовсе. Лестница из четырёх ступеней реализуется в
`ngx_http_waf_resolve_verdict()` явно и в этом порядке, иначе редирект от сервиса челленджа
начнёт перехватывать запросы, которые должны блокироваться.

**Из счёта следует только отказ.** Ступени челленджа в лестнице нет и порога под неё в
конфигурации не заведено: кому и когда доказывать, что он человек, решает сервис, который
челлендж ведёт, и присылает готовый `redirect` с адресом. Для кода это означает, что
единственное сравнение счёта с порогом — ступень 2, а единственное, что модуль делает с
присланным адресом, — проверяет его в `ngx_http_waf_msg_reply.c` по `waf_redirect_allow`
маршрута и отбраковывает ответ целиком, если тот не прошёл.

**Счёт живёт в `ctx`, а не в слоте.** Слот освобождается перед публикацией следующей волны,
поэтому сумма в нём не пережила бы переход между волнами. `ctx->score` — накопитель фазы,
`ctx->shadow` — теневая сумма пассивных; при переходе к фазе ответа оба
обнуляются, суммы фаз раздельные.

**`score` не останавливает волну.** Маска `slot->denied` заполняется только по `deny` и
`redirect`. Если считать отказом любой неразрешающий вердикт, следующая волна не
публикуется — а именно её инспекторы и должны увидеть накопленный счёт в `prior`.

**Веса нет.** Множитель `weight=` на вызове снят: очки ложатся в сумму как присланы, у
совещательного (`mode=vote`) `deny` — сотней. Диапазон вклада 0–100 и предел в 64 инспектора дают
потолок суммы 6400, так что переполнения `ngx_int_t` нет ни при каком входе, а число в аудите
совпадает с числом на проводе.

**Разбор поля `score` — это разбор недоверенного числа.** Правило то же, что и для
остальных полей ответа: диапазон 0–100 и только целое, всё остальное отбраковывает ответ
целиком со счётчиком. Подрезка до границы запрещена — она превращает ошибку инспектора в
тихо неверное решение. Отрицательные значения отвергаются не как «странный ввод», а как
нарушение инварианта, на котором держится замыкание фазы: неотрицательность делает сумму
монотонной, а пересечение порога — необратимым.

## Сборка

Модуль собирается против той же сборки nginx, которая используется в продакшене:
`configure`-флаги влияют на структуры, и модуль, собранный против других, даёт порчу
памяти, а не ошибку загрузки.

```sh
cd nginx-1.28.0
./configure --with-compat --add-dynamic-module=/path/to/waf/nginx/module
make modules
cp objs/ngx_http_waf_module.so /etc/nginx/modules/
```

То же самое в контейнере, с зафиксированной версией и флагами:

```sh
docker build --target artifact --output type=local,dest=./out .
```

Готовое окружение из nginx с модулем, шины NATS и двух тестовых инспекторов — в
../../deploy (`deploy`), там же проверочные маршруты и сквозной прогон.

Минимальная конфигурация (целевой синтаксис; парсер `waf_inspect` ещё не выкатан, живой
`deploy/nginx/nginx.conf` остаётся на старом API):

```nginx
load_module modules/ngx_http_waf_module.so;

http {
    waf_node_id edge-01;

    waf_bus nats://127.0.0.1:4222;

    waf_inspector ip   subject=waf.req.ip;
    waf_inspector sqli subject=waf.req.sqli;

    waf_deny_response blocked status=403;

    server {
        listen 8080;

        location / {
            waf                    on;
            waf_inspect ip   wave=0 timeout=5ms;
            waf_inspect sqli wave=1 timeout=15ms;
            waf_deadline           25ms block;

            proxy_pass http://127.0.0.1:8081;
        }

        location = /healthz { waf off; }
    }
}
```

Инспекторы без `waf_bus` — конфигурация, которая выглядит защищающей и не защищает:
публиковать некуда, и каждый запрос уходит в `waf_exception … bus`. Поэтому такая конфигурация
не загружается вовсе.
