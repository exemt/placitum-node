# internal/retain

Архивация: обменник → архив, с подменой локаторов в записи аудита.

Модуль не удаляет из обменника объекты, названные в `store.archive`, — владение
ключами переходит агенту. Здесь они забираются из Redis, кладутся в S3, локаторы
в записи подменяются архивными, запись публикуется, и только потом чистится
обменник.

Порядок двух последних шагов принципиален. Падение между ними оставляет верную
запись и осиротевший ключ, который доберёт `retain_ttl`. В обратном порядке
теряется запись, а объект остаётся в архиве без единой ссылки на себя — то есть
навсегда и невидимо.

```
Handle ──┬── archive пусто ─────────────────────────► publish
         ├── архив не настроен ── archive_error ────► publish ─► DEL
         ├── очередь полна ────── overload ─────────► publish ─► DEL
         └── очередь ── воркер ── корзины по виду
                    headers / args / body
                    flush: size или timeout
                    GET, PUT вспышкой секции
                    запись ждёт все свои секции ──► publish ─► DEL
```

Очередь ограничена, потому что `handoff.Serve` вызывает обработчик синхронно в
цикле чтения датаграмм, а у `unixgram` нет обратного давления: задержка здесь —
это переполненный буфер сокета и потерянные записи там. Переполнение не теряет
событие, теряет полезную нагрузку.

Своя причина у переполнения, а не общий `archive_error`: обратное давление
лечится ёмкостью очереди и числом воркеров, отказ хранилища — самим хранилищем,
и по логу это должно различаться без гадания.

`DEL` на двух деградировавших ветках делает не `Handle`, а отдельный чистильщик:
запись уже объявила объект недоступным, за ним не придёт никто, и держать его до
конца `retain_ttl` значит платить памятью обменника ровно там, где темп и без того
выше, чем справляется перенос. Канал чистки тоже ограничен — переполнился,
значит ключ снова доживает `retain_ttl`.

Воркер режет объект по `limit` из `store.archive` перед `PUT` и помечает
архивный локатор `truncated`. Режет именно он, а не модуль: в обменнике объект
лежит целиком, потому что его мог попросить инспектор. Пустой объект в архив не
едет вовсе — его локатор уезжает с причиной `empty`.

## Файлы

| Файл | Что в нём |
| --- | --- |
| `retain.go` | Пул, очередь, перенос одного объекта, деградация |
| `batch.go` | Три корзины: накопление PUT по виду, парковка записи |
| `redis.go` | Обменник: `GET` и `DEL`, RESP на стандартной библиотеке |
| `s3.go` | Архив: `PutObject` с тегом и подпись SigV4 |
| `config.go` | `WAF_RETAIN_*`, корзины, список узлов обменника, реквизиты из файла |

Клиенты свои, а не SDK: RESP — это две команды, а SigV4 — пять HMAC, тогда как
`aws-sdk-go-v2` и `go-redis` принесли бы разрешение регионов, свои ретраи и
полсотни транзитивных модулей ради одного `PutObject`. Блокировать здесь можно:
это не цикл событий nginx, и воркер не держит ничего, кроме себя.

## Настройка

Перечень переменных — `docs/nginx/agent/README.md`.
Раскладка бакетов и lifecycle — `docs/deployment.md`.

Ничего не задано — архивация выключена, и это не ошибка: модуль может её и не
просить. Задано криво — ошибка на старте: тихо деградировать в «архива нет»
значит однажды обнаружить пустой бакет вместо доказательной базы.
