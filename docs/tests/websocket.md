# Прогон вебсокета

```sh
node nginx/tests/ws/run.mjs
```

Приложение с WebSocket-эхо, NATS, Redis, настоящие инспекторы modsec и json,
nginx с модулем перед ними и клиент в самом прогоне. Кадры разбираются
побайтно: `ws.mjs` — своя реализация RFC 6455 на полторы сотни строк, без
библиотек. Библиотека собрала бы сообщение за нас и спрятала ровно то, что
здесь проверяется: маскирование, фрагментацию, опкоды и порядок.

Образы: `WAF_NGINX_IMAGE` (`waf-nginx`), `WAF_MODSEC_IMAGE`
(`waf-inspector-modsec`), `WAF_JSON_IMAGE` (`waf-json`). Инспекторы те же,
что на запросах, на своих subject `waf.frm.modsec` и `waf.frm.json`; json
идёт с профилем `ws` из поставки образа — чат с типами сообщений `msg` и
`join`, по схеме на тип.

## Что проверяется

Рукопожатие — обычный HTTP-запрос, и оно проходит фазу запроса целиком:
`101` с правильным `Sec-WebSocket-Accept`, зафиксированный подпротокол,
вердикт модуля в `X-WAF-Debug`, а на плохом `User-Agent` — `403` из
каталога и никакого апгрейда.

После `101` соединение забирает обработчик кадров. Семь сессий, каждая про
своё; первые пять — на `/ws/` (спрашивается только сторона клиента), две
последние — на `/ws2/`, где одна строка `waf_inspect frame` спрашивает обе
стороны у counter и rewrite:

1. **Контракт, CRS и кеш.** `{"type":"msg","text":"привет"}` дважды: первый
   раз проходит обоих инспекторов, второй — кеш вердикта
   (`waf_frame_cache frame:c2s ttl=10s` на `/ws/`, в логе `reason
   "FRAME_CACHE"`); эхо возвращается оба раза. `{"q":"1' OR 1=1-- "}` — CRS
   набирает порог (score 50), json типа не знает: Close 1008 с причиной из
   записи `ws_policy`, приложение кадра не видит. Это приёмочный тест этапа
   кадров.
2. **Схема типа.** `{"type":"msg"}` без обязательного `text`: для CRS чистый
   JSON, для контракта — нарушение схемы. Close 1008 только от json: так
   видно, что кадр судит именно схема.
3. **Контрольные кадры и s2c без инспекторов.** `join` по схеме возвращается
   эхом; слово `push-leak` внутри валидного сообщения заставляет приложение
   прислать кадр с ошибкой СУБД по своей инициативе — он доставляется
   клиенту: на `/ws/` сторону `s2c` никто не спрашивает, и кадр идёт мимо
   инспекции (кадрирование при этом разбирается); `ping` получает `pong`,
   `close` — ответный `close`; кадры сервера не маскированы.
4. **Двоичный кадр.** modsec его пропускает (`MODSEC_FRAME_BINARY`), json по
   политике `opcode` отказывает: контракт про текст. Close 1008.
5. **Фрагменты со сборкой.** `{"type":"msg",` + ping + `"text":` + `"hi"}`
   при `waf_frame_reassemble on`: модуль склеивает три фрагмента в буфере,
   судит сообщение целиком и отдаёт приложению одним кадром — эхо приходит
   одним текстовым кадром, ping между фрагментами получает pong, соединение
   живо.
6. **Подмена в обе стороны.** `hello badword` уходит приложению как
   `hello ***` — эхо отражает то, что получило, и по нему видно, что кадр
   переписан до апстрима. `token secret-123 here` клиент не трогает, эхо
   отдаёт оригинал, а клиент получает `token secret-*** here`: сторона
   `s2c` переписана до клиента. Соединение живо, Close не было.
   Отдельной сессией — **подмена собранного сообщения**: `hello bad` +
   `word` фрагментами, слово разрезано между кадрами, а маска видит его
   целиком: эхо `hello ***`, в записи кадра `fragments: 2`.
7. **Счётчик по соединению.** Шесть кадров подряд в корзину `ws_frames`
   ёмкостью пять по оси `conn`: заряд кадра виден суду того же кадра, и
   кадр, доливший корзину за порог, закрывает соединение Close 1008 из
   записи `ws_policy`; до приложения дошли не все шесть. Кеш на `/ws2/`
   включён, но счётчик отвечает `"cache": false`, и повторов из кеша там нет.
8. **Локальный слой на кадрах** (`/local/`, три сессии). Лимит
   `count=frames` по `$waf_conn_id` (2r/s burst=2): четвёртый кадр подряд
   отсекается до шины, Close 1008 из записи `ws_flood` («too many frames»).
   Проверка по набору `ws_binary` с `$waf_frame_opcode`: двоичный кадр —
   Close 1008 из `ws_policy`, до счётчика не доходит. Ограничитель
   `waf_frame_control_rate 2r/s`: из шести ping подряд pong приходят на
   первые два-три, остальные не пересылаются, соединение живо и следующий
   кадр данных доходит.
9. **Квота: лестница из двух корзин** (`/quota/`, профили `ws_quota` у
   counter и rewrite). Счётчик первой волной меряет каждый текстовый кадр
   клиента (`if: { direction: [c2s], opcode: [text] }`) в две корзины: `ws_err` по соединению на три кадра и `ws_ban` по адресу на
   шесть. Первые два кадра проходят эхом; с третьего корзина соединения
   полна, счётчик включает `rewrite_quota` (`do: active`: на маршруте тот
   стоит с `mode=off`, и до просьбы второй волны нет
   вовсе — в записи кадра он `state: "off"`) и просит его (`do: mutate`, повод
   `WS_QUOTA`) включить группу `quota_error`; вторая волна подменяет кадр сообщением
   `{"error":"quota exceeded"}` — приложение получает его вместо сообщения,
   эхо возвращает клиенту, соединение живо. Шестой кадр наполняет корзину
   адреса: счётчик пишет адрес в живой набор `blocklist` событием keeper, тот
   издаёт дельту, модуль применяет её в зеркало, и седьмой кадр закрывается
   локальным слоем — Close 1008 с именем набора, до приложения он не доходит;
   новое рукопожатие с того же адреса получает 403 ещё на фазе запроса.
   Keeper на стенде поддельный (`keeper.mjs`): истина набора без Postgres, с
   тем же проводом и тем же хешем (SipHash-2-4 под ключом эпохи); прогон
   проверяет, что зеркало не разошлось (`diverged` в логе нет).

Отдельно — рукопожатие websocket-пути: с предложением `permessage-deflate`
на `/ws/` эхо подтверждает расширение в 101 (снятия там нет), на `/ws2/`
модуль снимает его до проксирования и 101 приходит без расширения; обычный
GET на `/ws2/chat` получает 426 из записи `upgrade_required`, до приложения
не доходя.

В логе модуля: четырнадцать строк `allow phase request` на рукопожатия, три
`deny phase request` (плохой UA, GET без апгрейда, рукопожатие с
забаненного адреса), одна `stripped 1 websocket extension`, не меньше девяти
`allow phase frame` (сколько именно, зависит от того, сколько кадров седьмой
сессии успело до отказа), семь `deny phase frame`, четырнадцать строк `frame
session closed` с итогами обеих сторон, семь `frame payload rewritten` (три
на `/ws2/`, четыре ошибкой по квоте), две `message … reassembled from`, одна
`reason "FRAME_CACHE"`, по строке на отказ локального слоя (`local rate
limit exceeded`, `local block by dataset "ws_binary"` и `"blocklist"`), одна
`control frames above waf_frame_control_rate are dropped`, снапшот и дельта
набора `blocklist` и ни одного `diverged`. Счётчики строк — самый короткий
способ увидеть, что фаза кадров бежит и бежит ровно там, где должна.

Записи аудита ловит приёмник стенда шины (`../bus/agent.go`) на общем томе
сокета; стенд ждёт его строку готовности до старта nginx — датаграмма без
сокета молча теряется. На `/ws/` политика умолчания `deny`, на `/ws2/` —
`waf_audit_frames all`, на `/quota/` — тоже `all`. Проверяется: семь записей
кадров с `deny` (три из них с кодами `local_rate` и `local_list`), семь с
`rewritten` (одна — собранное сообщение с `fragments: 2`, четыре — кадры
квоты с `rewrite_quota` среди участников и просьбой `active` среди `actions`;
у двух тихих кадров квоты `rewrite_quota` стоит со `state: "off"`), кадры обеих
сторон, каждый кадр
под ray своего рукопожатия и адрес кадра (ray, сторона, номер) уникален, у
отказанного кадра есть срез полезной нагрузки; четырнадцать записей сессий
под ray рукопожатия, из них семь с отказом и двенадцать с кадрами
(рукопожатия без кадров — расширения и plain — тоже сессии), у каждой есть
причина закрытия, а итоги видят кеш (`frames_cached`), сборку
(`messages_reassembled`) и отброшенные контрольные кадры
(`control_dropped`). `WAF_WS_VERBOSE=1` печатает все записи.

Калибровку CRS на кадрах держит тест инспектора
`inspectors/modsec/internal/rules/frame_test.go` (сообщение чата — ноль
очков, инъекция — порог), контракт — `inspectors/json/internal/validate`
и `internal/schema/frame_test.go` на том же профиле `ws`. Профили `ws`
counter и rewrite лежат в образах (`inspectors/*/profiles/ws`), их разбор и
селекторы — `internal/config/frame_test.go`, применение —
`internal/measure/frame_test.go`, `internal/decide/frame_test.go` у обоих.
Образы берутся из `WAF_COUNTER_IMAGE` и `WAF_REWRITE_IMAGE`.

## Почему приложение своё, а не готовое

Оно должно уметь то, чего эхо-сервер обычно не умеет: отвечать по своей
инициативе. Направление `s2c` — половина модели кадров, и без инициативы
приложения его нечем проверить: всё, что вернулось на запрос клиента, — это
всё ещё разговор, начатый клиентом. Когда появится `frame:s2c`, строка про
`push-leak` меняется на ожидание Close.

## Нагрузка

```sh
node nginx/tests/ws/load.mjs                                   # лестница до упора на /echo/ и /pipe/
node nginx/tests/ws/load.mjs --paths /pipe/ --size 4k --seconds 20
node nginx/tests/ws/load.mjs --rates 100,300,800 --size 128 --paths /echo/,/frames/,/ws/
```

Из Git Bash — с `MSYS_NO_PATHCONV=1`: иначе `--paths /ws/` превращается в
`C:/Program Files/Git/ws/`, и рукопожатие получает 400.

Тот же стенд и тот же `ws.conf`, без rewrite: его `/ws2/` закрывает
соединение корзиной кадров и под поток не годится. Эхо одно, локаций
несколько, чтобы цена раскладывалась по слоям:

| Локация | Что стоит на пути | Что меряется |
| --- | --- | --- |
| `/echo/` | `waf off` — контекста фазы запроса нет, обработчик кадров к соединению не цепляется | эталон стенда: nginx-прокси, приложение, клиент |
| `/frames/` | снимок кадра в обменник, `gate`, инспекторов нет | кадрирование, буфер, Redis, аудит |
| `/pipe/` | счётчик на обеих сторонах (кадры клиента по соединению, байты приложения по адресу) и облегчённый CRS на кадрах клиента; `gate` на обеих сторонах, `waf_deadline 1s block` | боевой маршрут чата |
| `/ws/` | полный CRS + json на кадрах клиента, `gate`, дедлайн 1s | вся фаза с инспекцией, как в функциональном прогоне |
| `/ladder/` | лестница квоты: счётчик двух корзин первой волной и rewrite второй — записан `mode=off`, включается только просьбой `active`, под прогоном не зовётся вовсе; обе стороны, `waf_frame_reassemble on`, дедлайн 1s; корзины на десятки миллионов, порог не берётся | цена пути «две корзины → просьба → rewrite» на каждом кадре обеих сторон, и цена сборки с `--fragments N` |

`--fragments N` режет каждое сообщение клиента на N кадров (первый `text`
без fin, дальше `continuation`); эхо возвращает куски как получило, клиент
собирает их сам, поэтому `/echo/` с фрагментами — честный эталон той же
нагрузки, а разница с `/ladder/` — цена сборки и инспекции целого сообщения.
Стенд нагрузки поднимает и rewrite, и поддельный keeper (`keeper.mjs`):
без него набор `blocklist` на `/ladder/` не готов, и модуль писал бы ошибку
на каждом повторе снапшота. `--scale N` поднимает N экземпляров counter и
rewrite в одной queue group.

Цифры 06.09.2026 (Docker Desktop на Windows, 50 соединений, 8 с на
ступень, чисто — пока p99 не вырос втрое против первой ступени и никто не
закрыт):

| Локация, кадр | Один экземпляр | Три экземпляра |
| --- | --- | --- |
| `/echo/` 128 Б | до 3100/с, p50 ≈ 3 мс | — |
| `/frames/` 128 Б | до 4650/с, p50 2–4 мс | — |
| `/ladder/` 128 Б | до 150/с; на 250/с p50 24, p99 213 мс | до 250/с; на 400/с p50 34, p99 217 мс |
| `/ladder/` 1–12 КБ | до 250/с (p50 16, p99 97); на 400/с очередь пробивает дедлайн 1 с, Close 1011 | до 600/с (p50 29, p99 89); на 900/с p50 634 мс |
| `/ladder/` 1–12 КБ ×4 фрагмента | до 400/с (p50 52, p99 208); 600/с закрыто | — |

Пол задержки лестницы на малой нагрузке — p50 10–15 мс, p99 20–75 мс: на
сообщение четыре последовательных круга по шине (два кадра × две волны)
плюс поход счётчика в Redis на каждом кадре и put/del объекта модулем.
Потолок одного экземпляра — CPU счётчика (≈1.5–2 мс на кадр на этом
хосте, rewrite ≈1 мс), и он делится копиями; с тремя экземплярами на 600/с
никто не упёрся в ядро, а выше растёт хвост очередей на виртуальной сети
Docker Desktop, и на 900/с единственный воркер nginx доходит до 93 %. Сборка
фрагментов заметной цены не добавляет: те же 250–400/с, что без неё.

Счётчик `/pipe/` — профиль `wsload` из образа counter: корзины `ws_in`
(5000 кадров по соединению, остывает на 1000/с) и `ws_out` (256 МБ по
адресу, 50 МБ/с) сложены так, что честный клиент порога не берёт, а суд с
отказом на полной корзине есть — иначе профиль не показал бы цену пути
«измерил → судил». Облегчённый CRS — каталог `modsec-light` рядом с
`ws.conf`, подмонтированный в контейнер как профиль `light`: только
`901`, `941` (XSS), `942` (SQLi) и `949`; остальные семейства судят
заголовки, метод и путь, которых у кадра нет. Неизвестный профиль у modsec
на стенде — отказ, а не тихий откат на `default`: иначе прогон мерил бы
полный набор, думая, что облегчённый. `waf_hold frame:s2c monitor` модуль
пока отвергает на `nginx -t`, поэтому выдача приложения тоже ждёт
счётчика.

По умолчанию — лестница: со 100 сообщений в секунду, каждая ступень в
полтора раза выше (округление до 50), по десять секунд, пятьдесят
соединений, тела случайной длины от 1 до 12 КБ по контракту json
(`{"type":"msg","text":…}`). Лестница останавливается на первой плохой
ступени: закрытые соединения или эхо не вернулось за пять секунд слива —
«отказы»; сокет не принял предложенную скорость (меньше 95 % цели) — «не
принял»; p99 выше `--p99` (100 мс) и втрое выше первой ступени — «рост
задержек». `--rates` задаёт ступени явно и до упора не идёт.

Клиент — тот же `ws.mjs` в процессе прогона. Скорость держится
расписанием: тик раз в две миллисекунды досылает всё, что по расписанию
уже пора; у каждого соединения свой сдвиг внутри периода, иначе пятьдесят
сокетов шлют в один тик, и залп из 50 кадров по 12 КБ раз в полсекунды
упирается в 500 мс таймаута волны — клиенты чата так не ходят. Когда сокет
не принимает (кадр держится до вердикта, TCP упёрся в буферы), недосланное
списывается, а не догоняется залпом, — в отчёте видна предложенная
нагрузка, а не намерение. Каждое сообщение несёт номер, и по эху меряется
задержка «отправил → вернулось». Посреди ступени снимается `docker stats`
контейнеров, в конце — счётчики лога модуля: `allow`/`deny` кадров, `no
verdict`, причины закрытия сессий и строки ошибок.

Эталон без модуля идёт до 2050/с без потерь, nginx занят на 18 % ядра.
`/pipe/` чист до 400/с, на 600/с задержки взрываются: modsec занимает
пятнадцать ядер, очередь на шине растёт, p50 полсекунды. Закрытий при этом
нет — дедлайн модуля считается от чтения кадра, а очередь копится до него,
в TCP-буферах. Потолок ставит CRS, и ставит его длина кадра: тот же
инспектор с полным набором держал 800/с на кадрах по 128 байт (таблица
ниже), а облегчённый на кадрах в среднем 6,5 КБ отдаёт около 30 мс
процессора на кадр — правила прогоняют регулярные выражения и
преобразования по всему аргументу. Счётчик на обеих сторонах стоит около
миллисекунды на кадр и в потолок не упирается. Выше он поднимается второй
копией modsec, а не модулем.

`/ws/` на килобайтных кадрах не сравним: контракт json (`schema-chat_msg`)
режет `text` на 4096 символах, и такие кадры получают Close 1008 по схеме,
а не по нагрузке. Для него — ступени на 128 байтах:

Модуль без инспекторов не отличим от `waf off`: `/frames/` проходит все
ступени без потерь, nginx на 2000/с занят на 8–9 % ядра в обеих. `/ws/`
держит до 800/с с задержкой около десяти миллисекунд; на 1200 и 2000
закрываются по одному-пять соединений из пятидесяти: отдельный кадр не
получает вердикта за секунду — `no verdict (fail_timeout)`, политика
`block` из `waf_deadline`, клиенту Close 1011 «inspection unavailable».
`deny phase frame` при этом ноль: отказов по содержимому нет, только
дедлайн.

Что не меряется: `monitor` на кадрах (не реализован), подмена (rewrite не
поднят) и машина без Docker Desktop — цифры сравнимы между собой, а не с
прод. Лог модуля на стенде стоит на `info`, строка на кадр, и это тоже
часть цены nginx в таблицах.
