# Нагрузочный стенд

Методика и устройство стенда для конфигурации «балансировщик → N узлов nginx с модулем → NATS →
IP фильтр». Здесь топология, выбор инструментов и расчёты сайзинга; модель трафика,
сценарии и наблюдаемость вынесены в соседние документы.

| Документ | О чём |
| --- | --- |
| [traffic-model.md](traffic-model.md) | Из чего состоит случайный запрос, распределение размеров тела, воспроизводимость |
| [scenarios.md](scenarios.md) | Матрица сценариев, параметры и критерии pass/fail |
| [observability.md](observability.md) | Точки снимка, атрибуция задержки, чего измерить нельзя |

Стенд собран и запускается одной командой:

```powershell
cd nginx/tests/load
./scripts/run.ps1 -Scenario smoke              # 50 rps, минута, проверка что всё сходится
./scripts/run.ps1 -Scenario steady -Rate 5000 -Duration 5m -Edges 3 -Obs
```

Подробности — в разделе [Запуск](#запуск).

## Что измеримо сегодня

Топология из заголовка собирается целиком: клиент NATS в модуле есть, инспекторы отвечают через
шину. На стенде -- `ip`: самый дешёвый из четырёх, без тела и без CRS, чтобы замер не упирался
в инспектора. Отказ задаётся `X-Forwarded-For: 203.0.113.10` из blocklist.

**Нога «NATS → инспектор» измеряется отдельно.** У IP фильтра есть `ip-probe` --
симулятор модуля, который публикует сообщение того же формата на subject инспектора.

```sh
docker compose -f compose.load.yml exec inspector ip-probe --quiet --client-ip 8.8.8.8
```

Это эталон RTT без участия nginx, с которым сравнивается латентность инспектора, снятая модулем
через `X-WAF-Debug`. Потока он не даёт -- запросы идут строго по одному, -- поэтому потолок
инспектора по сообщениям в секунду пока не измеряется ничем, см. [bus-only](scenarios.md#bus-only).

Что не проверяется до этапа 7: удержание ответа и его инспекция. Соответствующие сценарии описаны,
но помечены этапом.

## Топология

```
                                      +-- edge-1 (nginx + модуль) --+
   k6 / wrk  --->  HAProxy  --------->+-- edge-2 (nginx + модуль) --+---> origin
       |                              +-- edge-N (nginx + модуль) --+
       |                                        |
       |  профиль direct: мимо балансировщика   |  core NATS
       +----------------------------------------+
                                                v
                                       NATS  <--->  инспектор x1
                                                    (queue subscribe)
```

Роли:

| Компонент | Зачем в стенде |
| --- | --- |
| Генератор | k6 в режиме постоянной интенсивности; wrk отдельным профилем для поиска потолка |
| HAProxy | Балансировщик перед узлами; масштабируется вместе с `--scale edge=N` |
| edge×N | Собственно объект измерения: nginx с модулем, отдельная конфигурация под нагрузку |
| origin | Заглушка приложения; обязана быть заведомо быстрее всего остального |
| NATS | Core NATS для горячего пути; JetStream не участвует, аудит появится на этапе 8 |
| Инспектор | inspectors/ip (`inspectors/ip`) — один subject и одно имя, но реплик сколько нужно: подписка идёт queue group |
| Обсервабилити | Prometheus, Grafana, cAdvisor, экспортер NATS — см. [observability.md](observability.md) |

### Почему HAProxy, а не nginx

Открытый nginx не умеет переразрешать имена в блоке `upstream`: `server ... resolve` — директива
nginx Plus. Значит `docker compose up -d --scale edge=N` потребовал бы генерации конфигурации
балансировщика на каждое значение N, и число узлов перестало бы быть параметром прогона.

У HAProxy это штатный режим: `server-template` разворачивается в набор слотов, а `resolvers`
опрашивает встроенный DNS Docker и заполняет их всеми A-записями сервиса.

```haproxy
resolvers docker
    nameserver dns 127.0.0.11:53
    hold valid 1s

backend edges
    balance roundrobin
    server-template edge- 16 edge:8080 check resolvers docker init-addr none
```

Побочная выгода — формат лога HAProxy отдельно показывает время ожидания в очереди, время
установления соединения и время ответа узла, что нужно для атрибуции задержки.

### Почему балансировщик обязан отключаться

Профиль `direct` бьёт в один узел мимо HAProxy. Без него нельзя ответить на вопрос, чья это
задержка: при насыщении балансировщик начинает выглядеть как медленный WAF. Разница между профилями
`direct` и `lb` на одинаковой интенсивности — это и есть цена балансировщика, и её нужно знать
численно, прежде чем интерпретировать любое другое число.

## Запуск

Нужен только Docker. Стенд собирает модуль сам из [nginx/module](../../../module), инспектора — из
inspectors/ip (`inspectors/ip`).

```powershell
cd nginx/tests/load

./scripts/run.ps1 -Scenario smoke                            # проверка, что всё сходится
./scripts/run.ps1 -Scenario steady -Rate 5000 -Duration 5m -Edges 3 -Obs
./scripts/run.ps1 -Scenario ceiling -Through direct          # потолок стенда, ветка waf off
./scripts/run.ps1 -Scenario steady -Rate 2000 -TimeoutRatio 0.05 -SilentRatio 0.02
```

В Linux и WSL то же самое длинными опциями: `./scripts/run.sh --scenario steady --rate 5000 --obs`.

Скрипт поднимает стенд, снимает состояние до нагрузки, запускает k6, снимает состояние после и
складывает всё в `results/<сценарий>-<время>/`.

Это не кнопка в контроллере. Короткий прогон по уже поднятому `deploy/` (без `--scale` и без
пересоздания края) — страница Трафик, `deploy/loadgen`.

| Артефакт | Что внутри |
| --- | --- |
| `report.txt` | Сводка: интенсивность, квантили обеих ветвей, добавленная задержка, неожидаемые коды |
| `summary.json` | Полная сводка k6 со всеми разрезами по тегам |
| `manifest.json` | Все параметры прогона, коммит и образы стенда — без него результат не воспроизводим |
| `stats.csv` | CPU и память по контейнерам, ряд с шагом 5 с |
| `before/`, `after/` | Снимки внутреннего состояния, см. [observability.md](observability.md) |

Стенд после прогона остаётся поднятым — разбирать результат почти всегда приходится по живому.
Снять состояние в любой момент, в том числе под нагрузкой:

```powershell
./scripts/inside.ps1
```

### Параметры прогона

Полный список с пояснениями — в [.env.example](../../../tests/load/.env.example); ключи `run.ps1` называются так же.
Чаще всего меняют эти.

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `-Scenario` | `smoke` | Что прогоняем, см. [scenarios.md](scenarios.md) |
| `-Rate`, `-Duration` | `2000`, `2m` | Целевая интенсивность и длительность |
| `-Edges`, `-Inspectors` | `1`, `1` | Число узлов nginx и реплик инспектора |
| `-Through` | `lb` | `lb` — через HAProxy, `direct` — мимо него |
| `-Deadline`, `-OnTimeout` | `200ms`, `block` | `waf_deadline <time> [pass\|block]` на узлах |
| `-ControlRatio` | `0.10` | Доля ветки `waf off`. Ноль означает, что добавленную задержку посчитать не из чего |
| `-AttackRatio`, `-ScoreRatio` | `0.05`, `0.05` | Доли явных отказов и вердиктов `score` (половина ниже порога, половина на нём) |
| `-RedirectRatio` | `0.01` | Доля вердиктов `redirect`, то есть челленджей: из счёта они не следуют, их присылает инспектор |
| `-SlowRatio`, `-TimeoutRatio`, `-SilentRatio` | `0.02`, `0`, `0` | Доли ответов внутри дедлайна, после него и молчания инспектора |
| `-SlowDelayOk`, `-SlowDelayTimeout` | `50`, `400` | Паузы инспектора в миллисекундах для двух предыдущих долей |
| `-AbortRatio` | `0` | Доля клиентов, обрывающих соединение во время ожидания вердикта |
| `-DebugRatio` | `0.01` | Доля запросов через `/debug/` с `waf_debug_header on`: из них берётся латентность инспектора |
| `-BodyProfile` | `mixed` | `mixed` — тела до 64 KB, `large` — до 1.3 MB на низкой интенсивности |
| `-Warmup` | `30s` | Окно прогрева: запросы в нём помечаются `phase:warmup` и в пороги не идут |
| `-Seed`, `-CorpusSize` | `20260813`, `20000` | Зерно и размер корпуса, см. [traffic-model.md](traffic-model.md) |
| `-Obs` | выкл. | Prometheus, Grafana, cAdvisor и экспортер NATS |
| `-Pin` | выкл. | Закрепление контейнеров за ядрами, [compose.pin.yml](../../../tests/load/compose.pin.yml) |

Вердиктами управляет генератор, а не конфигурация узла: IP фильтр смотрит
на `X-Forwarded-For`. Отказ -- `203.0.113.10` из blocklist, остальное --
публичный адрес вне списков.

### Порты

Наружу выходят только порты управления, и они смещены на 10000, чтобы стенд поднимался рядом с
окружением из deploy/ (`deploy`), которое занимает 8080, 8081, 8404, 4222, 8222 и 6379.

| Порт | Что |
| --- | --- |
| 18080 | HAProxy — только для ручных проверок curl'ом |
| 18404 | Статистика HAProxy и её `/metrics` |
| 18222 | Мониторинг NATS: `/varz`, `/connz`, `/subsz` |
| 19090, 13000 | Prometheus и Grafana, профиль `-Obs` |

Путь нагрузки наружу не выходит вовсе: k6 работает контейнером в той же docker-сети.

## Выбор инструмента

Два инструмента с непересекающимися ролями.

**k6 — источник всех чисел, на которых стоят пороги.** Причина одна и она принципиальна: режим
`constant-arrival-rate` задаёт интенсивность, а не число соединений. Инструмент с фиксированным
пулом соединений (закрытая модель) при росте задержки просто реже отправляет запросы — нагрузка
падает вслед за деградацией, очередь не растёт, и измеренный квантиль оказывается тем лучше, чем
хуже ведёт себя система. Это coordinated omission, и для WAF, вся суть которого в добавленной
задержке, он превращает измерение в самообман. Открытая модель, наоборот, продолжает подавать
запросы и показывает накопление в полёте — то самое, что упирается в `waf_max_inflight` и в
соединения.

Вторая причина прозаичнее: пороги в k6 — часть скрипта (`thresholds`), поэтому прогон сам
завершается с ненулевым кодом при нарушении бюджета и годится как шаг CI без внешнего анализатора.

Порог на `dropped_iterations` стоит во всех сценариях и обязателен: если k6 не смог выдержать
заданную интенсивность, измерена не система, а генератор, и остальные числа прогона недействительны.
Порога «нет ошибок» при этом нет и быть не может — 403 при вердикте `deny` и 503 при
`waf_deadline ... block` являются успехом. Вместо него генератор вычисляет ожидаемый код для каждого
запроса из его флавора и считает расхождения счётчиком `unexpected_status`, порог на который —
`count==0`.

**wrk с Lua — только поиск потолка.** Он быстрее k6 в разы на один и тот же CPU, потому что в
горячем пути нет интерпретатора JS, и это ровно то, что нужно для вопроса «сколько вообще держит
стенд». Латентность из wrk в критерии не входит никогда — по причине из предыдущего абзаца. Профиль
`wrk/corpus.lua` использует тот же корпус, что и k6, чтобы потолок измерялся на том же трафике.

Что рассмотрено и отклонено:

| Вариант | Почему нет |
| --- | --- |
| vegeta | Честная открытая модель и корректные гистограммы, но рандомизация — только через заранее выписанный файл целей: тела в сотни килобайт превращают корпус в гигабайты на диске, а логика выбора варианта уезжает из скрипта в генератор файла |
| Только wrk | Пороги, ветвление по маршрутам и машиночитаемый отчёт пришлось бы писать на Lua с нуля |
| Locust, Gatling | Стоимость на запрос несовместима с десятками тысяч rps на одной машине |
| ab, hey | Нет ни рандомизации, ни открытой модели |

## Что считается результатом

**Главное число — добавленная задержка, а не абсолютная.** Абсолютная включает origin,
балансировщик, сеть и сам генератор, и меняется от прогона к прогону; она ничего не говорит о
модуле.

```
добавленная = p99(branch:waf, flavor:normal) − p99(branch:control, flavor:normal)
```

Обе ветки обязаны обстреливаться **в одном прогоне**, на одной машине, при одинаковой суммарной
интенсивности: маршрут `/api/` с `waf on` и контрольный `/nowaf/` с `waf off`. Сравнение с числом из
вчерашнего прогона недействительно, потому что фон машины другой.

Разрез `flavor:normal` в формуле обязателен. Флаворы с заданной паузой — `slow_ok`, `slow_timeout`,
`silent` — измеряли бы паузу, которую мы сами и задали, и чем больше их доля в прогоне, тем сильнее
они утянули бы p99 ветки `waf` вверх. Сводка считает добавленную задержку по этому разрезу; в
Grafana его надо выбирать руками.

Это число и есть то, что стоит собственно механика ожидания: слот, таймер, повторный вход в фазы,
публикация, RTT шины и работа инспектора без искусственной паузы. Оно сравнивается с бюджетом из
`docs/deployment.md`, где на всю фазу запроса отведено 7 ms
на p99, и оно же должно оставаться плоским при росте интенсивности. Рост с интенсивностью означает
очередь где-то внутри, и её надо искать по [observability.md](observability.md).

Разложить его на составляющие стенд сегодня не умеет: `X-WAF-Debug` показывает ожидание вердикта
целиком, но не отделяет шину от инспектора. Что для этого нужно — в
[observability.md](observability.md#чего-измерить-нельзя-сегодня).

Второе обязательное число — **доля неожидаемых кодов ответа**. Не «ошибок»: 503 в сценарии с
`waf_deadline ... block` ожидаем и является успехом, а 200 там же — провал. Поэтому у каждого
сценария в [scenarios.md](scenarios.md) свой список допустимых кодов, а не общий порог на `http_req_failed`.

```
├── .env.example                    все параметры прогона с пояснениями

│   ├── main.js                     точка входа, сценарий выбирается переменной
│   └── lib/
│       ├── env.js                  числа из окружения с отказом на NaN

│       └── options.js              сценарии и пороги

├── lb/haproxy.cfg                  server-template + resolvers на DNS docker
├── edge/nginx.load.conf.template   конфигурация узла под нагрузку, не из deploy/
├── origin/nginx.conf
├── nats/nats-server.conf           без JetStream: он в горячий путь не входит
├── obs/
│   ├── prometheus.yml
│   └── grafana/                    datasource и дашборд стенда

│   ├── inside.ps1, inside.sh       снимок внутреннего состояния
│   └── stats.ps1, stats.sh         выборка CPU и памяти в CSV
└── results/                        артефакты прогонов, в репозиторий не идут
```

Конфигурация узла — шаблон, а не готовый файл: `waf_deadline` с политикой,
`waf_max_inflight` и число воркеров подставляет `envsubst` при старте контейнера по явному списку
имён. Явный список обязателен: без него `envsubst` съел бы и переменные самого nginx.

Конфигурация узла берётся не из deploy/ (`deploy`), а своя: там окружение для отладки, с
`access_log` в stdout, `error_log info` и `worker_connections 1024`. Под нагрузкой каждое из этих
значений искажает результат.

## Сайзинг

### Нагрузка на шину

По формуле из `docs/deployment.md` каждый запрос даёт
по два сообщения на каждого опрашиваемого инспектора:

```
сообщений/с = RPS × 2 × инспекторов
```

| RPS | Инспекторов | Сообщений/с |
| --- | --- | --- |
| 2 000 | 1 | 4 000 |
| 10 000 | 1 | 20 000 |
| 10 000 | 3 | 60 000 |
| 30 000 | 1 | 60 000 |

Для одного узла NATS это немного. Узкое место здесь не шина, а единственный инспектор: 20 000
сообщений в секунду означают 10 000 разборов JSON и 10 000 ответов в одном процессе на Node.
Инспектор должен уметь быть узким местом намеренно — для этого есть паузы, задаваемые на каждый
запрос (`-SlowDelayOk`, `-SlowDelayTimeout`), — и не быть им случайно: поэтому он подписывается
очередью (`queue subscribe`) и масштабируется ключом `-Inspectors`, даже когда в конфигурации
прогона его экземпляр один.

Одной реплики на 10 000 rps не хватает: в прогонах этого порядка ставьте `-Inspectors 4`, иначе
измеряется цикл событий Node, а не модуль.

### Соединения и слоты

Обе величины выводятся из одного и того же — числа запросов в полёте (закон Литтла):

```
в полёте = RPS × полная_задержка
```

Слот занимается на время ожидания вердикта и сравнивается с `waf_max_inflight` **на воркер**;
соединения живут дольше (клиентское плюс к origin) и сравниваются с `worker_connections`.

Расчёт для стенда с четырьмя воркерами на узел — столько, а не `auto`, потому что бюджет CPU надо
контролировать:

| Сценарий | RPS | Задержка | В полёте | На воркер |
| --- | --- | --- | --- | --- |
| `steady`, паузы нет | 10 000 | ~3 ms | 30 | 8 |
| `steady`, паузы нет | 30 000 | ~3 ms | 90 | 23 |
| `deadline-mix`, доля медленных | 10 000 | 200 ms по дедлайну | до 2 000 | до 500 |
| `inflight-pressure`, пауза всем | 10 000 | 200 ms | 2 000 | 500 |

Отсюда два вывода, оба неочевидные.

**Штатные лимиты на рабочих интенсивностях не достигаются даже близко.** Без искусственной паузы в
полёте держится меньше десятка запросов на воркер против `waf_max_inflight 4096`. Исчерпание слотов
на осмысленной задержке недостижимо в принципе: чтобы упереться, нужны либо секунды на вердикт, либо
намеренно заниженный `waf_max_inflight`. Сценарий `inflight-pressure` идёт обоими путями сразу —
поднимает дедлайн, чтобы пауза в 200 ms была допустимой, и опускает лимит до 256, чтобы его вообще
можно было пробить.

**`worker_connections` упирается раньше слотов.** Соединений вдвое больше запросов в полёте, а
умолчание nginx на порядок меньше лимита слотов: 1024 против 4096. В сценариях с большой задержкой
при четырёх воркерах это достигается. В конфигурации узла для стенда — `worker_connections 65536` и
запас по файловым дескрипторам; стоит это ничего, а диагностировать «упёрлись в лимит соединений» по
симптому «модуль тормозит» дорого.

### Полоса

Про неё забывают, а она отсекает половину замысла:

| RPS | Среднее тело | Поток |
| --- | --- | --- |
| 10 000 | 8 KB | 640 Mbit/s |
| 10 000 | 64 KB | 5 Gbit/s |
| 10 000 | 1 MB | 80 Gbit/s |

Десятки тысяч запросов в секунду с крупными телами на одной машине недостижимы, и никакая настройка
этого не меняет. Поэтому оси разведены: смешанный профиль ограничен телами до 64 KB, а крупные тела
проверяются отдельным профилем на низкой интенсивности, где важен не rps, а корректность работы с
размером. Подробности распределения — в [traffic-model.md](traffic-model.md).

### Бюджет машины

Ориентир для 24 логических ядер и 32 GB. Раскладка задаётся `cpuset` в `compose.load.yml`: без
закрепления генератор и объект измерения конкурируют за одни ядра, и результат зависит от планировщика.

| Компонент | Ядра | Примечание |
| --- | --- | --- |
| k6 | 4 | При экономном скрипте хватает на 20–30k rps |
| HAProxy | 2 | В профиле `direct` не запускается |
| edge×3 | 6 | По 4 воркера, `cpuset` на узел |
| origin | 2 | Должен оставаться незаметным |
| NATS | 2 | |
| Инспектор | 3 | |
| Обсервабилити | 2 | В прогонах на потолок отключается |
| Резерв | 3 | Хост, WSL2, docker |

Честные ожидания на этой конфигурации: 10 000 rps — рабочий режим с запасом; 20–30 000 rps —
достижимо на урезанном стенде (профиль `direct`, без обсервабилити, `access_log off`, тела не
крупнее нескольких килобайт); больше — нужна отдельная машина под генератор.

## Что портит результат

**Публикация портов в Windows.** Пробрасывание порта наружу из Docker Desktop идёт через прокси
между Windows и WSL2, и это жёсткий потолок по пропускной способности и источник дополнительных
задержек в хвосте. Генератор поэтому запускается контейнером в той же docker-сети, что и стенд, а
наружу выходят только порты управления. Порт 18080 опубликован для ручных проверок curl'ом; прогон
«из PowerShell по localhost:18080» измеряет прокси Docker Desktop, а не WAF.

**Десятичная запятая.** PowerShell форматирует `[double]` по текущей локали, и на русской системе
`0.05` уходит в окружение как `"0,05"`. `Number("0,05")` в JavaScript возвращает не ошибку, а `NaN`,
а любое сравнение с `NaN` ложно — доля трафика молча превращается в ноль. Прогон при этом проходит,
все пороги зелёные, а ветки трафика в нём просто нет. `run.ps1` приводит числа к инвариантной
культуре, а `k6/lib/env.js` отвергает значение с запятой с явным сообщением: тихий `NaN` здесь
опаснее упавшего прогона.

**Логи в горячем пути.** `access_log` в stdout контейнера — это запись в docker-демон на каждый
запрос. В конфигурации узла для стенда `access_log off` по умолчанию; там, где лог нужен для
атрибуции, он пишется в tmpfs с `buffer=64k flush=1s` и компактным форматом. `error_log` — уровень
`warn`, потому что диагностика модуля на `info` пишет строку на каждое срабатывание дедлайна, а в
сценарии `deadline-mix` это тысячи строк в секунду.

**Отсутствие keepalive.** Без него каждый запрос — новое соединение, и стенд упирается в диапазон
эфемерных портов и в `TIME_WAIT` задолго до любого лимита nginx. Keepalive обязателен на всех трёх
участках: генератор → HAProxy, HAProxy → edge, edge → origin (последнее — `upstream` с `keepalive`
и `proxy_http_version 1.1`).

**Параметры ядра.** Из них в compose задано только то, что действительно работает в Docker Desktop:
`ulimits.nofile` на узлах и балансировщике, `backlog` в `listen` у nginx, `maxconn` у HAProxy.
`sysctls` вроде `net.core.somaxconn` намеренно не выставляются: в WSL2 они относятся к общему ядру
виртуальной машины, и задание их на контейнер либо игнорируется, либо влияет на весь хост — то есть
на все прочие запущенные проекты. Переполнение таблицы `conntrack` на bridge-сети лечится
keepalive'ом, а не увеличением таблицы; если keepalive везде включён, до неё не доходит.

HAProxy требует примерно `2 × maxconn` файловых дескрипторов и отказывается стартовать, если
`ulimit` меньше. Это ровно та ошибка, которая выглядит как «балансировщик не поднялся» без
объяснений, поэтому числа в `haproxy.cfg` и `ulimits` в compose согласованы: 60000 против 200000.

**Прогрев.** Первые секунды содержат установление соединений, заполнение кешей и раскрутку JIT и в
k6, и в инспекторе на Node. Генератор помечает каждый запрос тегом `phase`, а пороги и сводка
считаются по разрезу `phase:measure`; окно задаётся ключом `-Warmup` и по умолчанию равно 30
секундам. Отбрасывание «на глаз» при разборе результата не требуется.
