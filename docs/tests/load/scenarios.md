# Сценарии и критерии

Матрица прогонов: что каждый доказывает, на каких параметрах идёт и по какому признаку считается
пройденным. Устройство стенда — в [README.md](README.md), состав трафика — в
[traffic-model.md](traffic-model.md).

## Правила, общие для всех сценариев

Нарушение любого из них делает результат недействительным независимо от того, что показали графики.

**Ветка сравнения обязательна.** В каждом прогоне часть трафика идёт на контрольный маршрут с
`waf off`. Итоговое число — разница квантилей между ветками, а не абсолютная задержка; обоснование в
[README](README.md#что-считается-результатом).

**Генератор обязан успевать.** Порог `dropped_iterations == 0` стоит во всех сценариях. Если k6 не
выдержал заданную интенсивность, измерен генератор.

**Первые 30 секунд отбрасываются.** Прогрев соединений, кешей и JIT не входит в статистику.

**Коды ответа проверяются по списку сценария.** Общего порога «нет ошибок» не существует: 503 в
сценарии с `waf_deadline ... block` — успех, а 200 там же — провал.

**Прогон без манифеста не считается.** Сид корпуса, версии, профиль и раскладка `cpuset` пишутся
рядом с результатом, см. [traffic-model.md](traffic-model.md#воспроизводимость).

Порядок первого прогона: `rig-ceiling` → `smoke` → `steady`. До получения потолка стенда остальные
числа интерпретировать нельзя.

Сценарий здесь — это методика, а не строка в конфигурации. В генераторе форм подачи нагрузки всего
пять (`-Scenario`), остальное задаётся долями трафика и политиками узла, потому что различаются эти
прогоны составом трафика, а не тем, как он подаётся.

Ниже — минимальная форма каждой команды; полные, с топологией и наблюдаемостью, приведены в разделах
сценариев.

| Сценарий | Команда |
| --- | --- |
| `rig-ceiling` | `.\scripts\run.ps1 -Scenario ceiling -Through direct`, затем то же с `-Through lb` |
| `smoke` | `.\scripts\run.ps1 -Scenario smoke` |
| `steady` | `.\scripts\run.ps1 -Scenario steady -Rate 10000 -Duration 10m` |
| `ramp-to-knee` | `.\scripts\run.ps1 -Scenario ramp -Rate 20000` |
| `inflight-pressure` | `.\scripts\run.ps1 -Scenario steady -Rate 10000 -MaxInflight 256 -Deadline 500ms -SlowRatio 0.9 -SlowDelayOk 200` |
| `deadline-mix` | `.\scripts\run.ps1 -Scenario steady -Rate 10000 -TimeoutRatio 0.02 -SilentRatio 0.01` |
| `abort-storm` | `.\scripts\run.ps1 -Scenario steady -Rate 10000 -AbortRatio 0.3 -Duration 15m` |
| `soak-10m` | `.\scripts\run.ps1 -Scenario soak -Rate 10000 -AbortRatio 0.05 -TimeoutRatio 0.02` |
| `reload-under-load` | `-Scenario steady -Duration 10m` плюс перезагрузка в соседней консоли, см. ниже |
| `bus-only` | `docker compose -f compose.load.yml exec inspector node src/probe.ts --count 2000 --quiet` |
| `bus-fault` | `-Scenario steady` плюс воздействие в соседней консоли, см. ниже |

На bash то же самое: `./scripts/run.sh --scenario steady --rate 10000 --duration 10m`, ключи
совпадают с точностью до записи (`-SlowDelayOk` → `--slow-delay-ok`).

Все перечисленные сценарии закреплены за этапами 1–2, которые в модуле закрыты, кроме
`reload-under-load`: дренаж висящих вердиктов при завершении воркера — этап 13. Функциональная
проверка тех же свойств без нагрузки — `tests/e2e`.

## rig-ceiling

**Цель.** Узнать, сколько держит стенд без модуля. Это верхняя граница для всех остальных чисел:
если стенд насыщается на 18 000 rps, замер модуля на 20 000 rps измеряет стенд.

| Параметр | Значение |
| --- | --- |
| Маршрут | Контрольный, `waf off` |
| Интенсивность | Ступени от 5k, шаг 5k, по 60 с |
| Профили | `direct` и `lb`, двумя прогонами |
| Тело | Профиль `mixed` |

**Что ловит.** Насыщение генератора, балансировщика, origin, сети bridge. Разница между `direct` и
`lb` даёт цену балансировщика в явном виде.

**Критерии.** Прогон не «проходит» и не «падает» — он даёт число. Записываются: интенсивность, при
которой появляется первый `dropped_iterations`; интенсивность, при которой p99 контрольной ветки
превышает удвоенное значение на минимальной ступени; загрузка CPU по контейнерам в этой точке.
Дальнейшие сценарии обязаны идти на интенсивности не выше 70 % от найденного потолка.

## smoke

**Цель.** Проверить сборку стенда до того, как тратить время на длинный прогон.

| Параметр | Значение |
| --- | --- |
| Интенсивность | 50 rps, 60 с |
| Трафик | Все флаворы, включая контрольную ветку |

**Критерии.** `unexpected_status` равен нулю — то есть каждый флавор дал ровно тот код, который
следует из его вердикта и политик узла: `allow` → 200, `deny` → 403, счёт ниже порога → 200, счёт на
пороге отказа → 403, `redirect` → 303, ответ после дедлайна и молчание инспектора → 503 при
`waf_deadline ... block`. Обе ветви в сводке непусты, добавленная задержка — единицы миллисекунд. В
`error_log` нет неожиданных записей уровня `warn` и выше (`results/<прогон>/after/edge-log.txt`).

Пустая контрольная ветка в сводке — отдельный симптом, а не мелочь: он означает, что доля трафика
где-то потерялась (например [десятичной запятой](README.md#что-портит-результат)), и добавленную
задержку в этом прогоне считать не из чего.

## steady

**Цель.** Основной замер: во что обходится модуль на рабочей интенсивности.

| Параметр | Значение |
| --- | --- |
| Интенсивность | 2 000 / 5 000 / 10 000 / 20 000 rps, отдельными прогонами |
| Длительность | 10 минут на точку |
| Задержка вердикта | Нет: основная масса трафика идёт без искусственной паузы в инспекторе |
| `-Deadline` | `200ms` |
| Тело | `-BodyProfile mixed` |
| Ожидаемые коды | 200, плюс доли отказов и редиректов согласно `-AttackRatio`, `-ScoreRatio` и `-RedirectRatio` |

```powershell
foreach ($r in 2000, 5000, 10000, 20000) {
    .\scripts\run.ps1 -Scenario steady -Rate $r -Duration 10m -Edges 2 -Inspectors 4 -Obs
}
```

Замер идёт по флавору `normal` — тому, где инспектор отвечает сразу. Флаворы с заданной паузой из
основной пары метрик исключены: иначе p99 ветки `waf` измерял бы паузу, которую мы сами же и задали.
Поэтому «задержка вердикта» здесь не параметр прогона, а то, что мы измеряем.

**Что ловит.** Стоимость механики ожидания и её зависимость от интенсивности.

**Критерии.**

- Добавленная задержка на p99 не растёт при переходе от 2 000 к 10 000 rps более чем в полтора раза.
  Рост означает очередь внутри, и её надо найти. Здесь она же и есть цена модуля целиком: паузы в
  инспекторе нет, вычитать из результата нечего.
- Добавленная задержка на p99 укладывается в бюджет фазы запроса из
  `docs/deployment.md` — 7 ms.
- Доля неожидаемых кодов равна нулю.
- `dropped_iterations` равен нулю.
- RSS воркеров на конец прогона не выше, чем на пятой минуте.

## ramp-to-knee

**Цель.** Найти точку перелома и назвать, что именно упёрлось.

| Параметр | Значение |
| --- | --- |
| Интенсивность | Ступени по 60 с до нарушения бюджета |
| Условие останова | p99 добавленной задержки выше 50 ms либо появление неожидаемых кодов |

Порог 50 ms взят не с потолка: это значение алерта на p99 фазы из
`docs/operations.md`, то есть граница, за которой поведение уже
считается аварийным в эксплуатации.

**Критерии.** Отчёт содержит интенсивность перелома и виновника: CPU воркеров nginx, CPU инспектора,
глубина очереди в шине, исчерпание слотов, соединения. Прогон без названного виновника считается
незавершённым — «стало плохо на 14 тысячах» не является результатом.

## inflight-pressure

**Цель.** Проверить, что исчерпание таблицы слотов даёт политику `waf_exception … bus`, а не аварию.

Как показано в [расчёте](README.md#соединения-и-слоты), на осмысленной задержке штатный
`waf_max_inflight 4096` недостижим: чтобы упереться, потребовались бы секунды на вердикт. Поэтому
давление создаётся снижением лимита, а не ростом задержки.

| Параметр | Значение |
| --- | --- |
| `-MaxInflight` | 256 |
| `-EdgeWorkers` | 4, при одном узле |
| Интенсивность | 10 000 rps |
| Задержка вердикта | `-SlowDelayOk 200` почти всему трафику, при `-Deadline 500ms` |
| `waf_exception … bus` | `pass` и `deny`, двумя прогонами, переменной `WAF_ON_BUS_ERROR` |

```powershell
.\scripts\run.ps1 -Scenario steady -Rate 10000 -Duration 10m `
                  -Edges 1 -EdgeWorkers 4 -Inspectors 4 `
                  -MaxInflight 256 -Deadline 500ms `
                  -SlowRatio 0.9 -SlowDelayOk 200 -AttackRatio 0 -ScoreRatio 0 `
                  -RedirectRatio 0
```

Арифметика подобрана так, чтобы лимит был заведомо пробит, а дедлайн — заведомо нет: при 10 000 rps и
паузе 200 ms в полёте держится около 2 000 запросов, на четыре воркера это 500 на каждый против
лимита 256. Дедлайн в 500 ms при этом не срабатывает, и 503 в прогоне могут появиться только от
исчерпания слотов — иначе два разных отказа было бы не различить.

Ожидаемый код генератор считает по задержке и дедлайну, про лимит слотов он не знает. Поэтому в
прогоне с `block` `unexpected_status` заведомо ненулевой и критерием не является; он и есть та самая
доля, которой не хватило слота.

**Что ловит.** Ветку `slot_acquire() == NULL` в
[ngx_http_waf_handler.c](../../../module/src/runtime/ngx_http_waf_handler.c), где отказ выдачи слота
переводится в `ST_BUS_ERROR`. Заодно — что таблица слотов возвращается в исходное состояние после
снятия нагрузки.

**Критерии.**

- При `pass` запросы, которым не хватило слота, проходят с 200; при `block` получают 503. Иных кодов
  нет.
- Ни одного падения воркера, ни одной записи `[alert]` или `[emerg]` в `error_log`.
- После снятия нагрузки прогон `smoke` проходит полностью: слоты освободились, а не залипли.
- RSS воркеров возвращается к доудачному значению.

## deadline-mix

**Цель.** Проверить обе политики `waf_deadline` под нагрузкой и убедиться, что ответ, пришедший
после истечения дедлайна, безвреден.

Задержку и молчание IP фильтр не умеет: он отвечает сразу. Сценарий
остаётся в матрице как проверка дедлайна модуля, но доли `-TimeoutRatio` и
`-SilentRatio` с `ip` дают обычный allow -- инспектор не молчит.

| Параметр | Значение |
| --- | --- |
| Раскладка | `-SlowRatio 0.02 -TimeoutRatio 0.02 -SilentRatio 0.01`, остальное — обычный allow |
| `-Deadline` | `200ms` |
| Задержки | `-SlowDelayOk 50`, `-SlowDelayTimeout 400` (переменные `SLOW_DELAY_*`) |
| Интенсивность | 10 000 rps |
| `-OnTimeout` | `block` и `pass`, двумя прогонами |

Молчание и опоздавший ответ разведены намеренно: слот освобождается в них по-разному — в первом
случае по таймеру дедлайна и больше никогда, во втором по таймеру, а затем в него же приходит
ненужный ответ. Это разные пути в модуле, и нагрузить нужно оба.

Отдельный прогон стоит сделать с задержкой ровно на границе (`-SlowDelayTimeout 200` при
`-Deadline 200ms`): гонка между таймером дедлайна и ответом инспектора не обязана разрешаться в одну
сторону, но обязана давать корректный исход в обе, а не смесь из корректного и повреждённого.
Ожидаемый код у генератора в этой точке вычислить нельзя, поэтому `unexpected_status` там не
критерий — критерий в том, что кодов ровно два, 200 и 503, и нет ни одной записи `[alert]`.

**Что ловит.** Главное — переиспользование слота. Опоздавший на 200 мс ответ приходит тогда, когда
слот уже выдан другому запросу; защита здесь — поколение в `rid` (`(gen << 24) | index`). Под
нагрузкой в 10 000 rps слоты оборачиваются быстро, и это единственный режим, в котором ошибка
сравнения поколений вообще проявится.

**Критерии.**

- `unexpected_status` равен нулю. Генератор знает и заданную задержку, и дедлайн, поэтому ожидаемый
  код считает сам: доля 503 при `block` обязана совпасть с суммой `TIMEOUT_RATIO` и `SILENT_RATIO`
  ровно, а не приблизительно.
- При `pass` все запросы получают 200, а задержка медленных равна `waf_deadline`, а не 400 ms.
- Ни одного ответа с чужим вердиктом: `rid` в `X-WAF-Debug` на маршруте `/debug/` совпадает с тем,
  что инспектор видел в запросе, и в логе нет записей о доставке в несуществующий слот.
- Ни одной записи `[alert]` или `[emerg]`.

## abort-storm

**Цель.** Проверить освобождение слота при обрыве клиента во время ожидания — прямой критерий выхода
этапа 1.

| Параметр | Значение |
| --- | --- |
| Задержка вердикта | `-SlowDelayTimeout 400` |
| Таймаут клиента | Десятая часть дедлайна, но не меньше 5 ms — обрыв гарантирован |
| Доля обрывающихся | `-AbortRatio 0.3` |
| Интенсивность | 10 000 rps |
| Длительность | 15 минут |

```powershell
.\scripts\run.ps1 -Scenario steady -Rate 10000 -Duration 15m `
                  -AbortRatio 0.3 -SlowDelayTimeout 400 -Edges 2 -Inspectors 4
```

Таймаут клиента ключом не задаётся: генератор берёт десятую часть дедлайна. Важно только то, что он
заведомо меньше задержки вердикта, конкретная величина роли не играет.

Оборванные запросы считаются отдельно и в `unexpected_status` не попадают: у них нет кода ответа, и
сравнивать не с чем. В сводке это строки «оборвано клиентом» и «обрыв не успел» — второй счётчик
показывает запросы, на которые ответ всё-таки пришёл раньше обрыва. Ненулевое значение там не
ошибка, но означает, что часть трафика проверила не тот путь, ради которого сценарий запускался; если
их много, задержку вердикта нужно поднять.

**Что ловит.** Путь через `ngx_http_test_reading`, который модуль ставит на время ожидания, и
разрыв связи контекста со слотом через `ngx_pool_cleanup_add()`. Утечка слота проявится не сразу:
таблица на 4096 записей на воркер при 3 000 обрывов в секунду исчерпается за секунды, и дальше
пойдут отказы по `waf_exception request bus` — характерный признак.

**Критерии.**

- Доля отказов у необорвавшихся 70 % трафика равна нулю на всём прогоне. Рост её со временем —
  утечка слотов.
- RSS воркеров на пятнадцатой минуте не выше, чем на третьей.
- Число открытых файловых дескрипторов не растёт.
- После снятия нагрузки `smoke` проходит полностью.

## soak-10m

**Цель.** Критерий выхода этапа 1 из `docs/roadmap.md`: десять миллионов
запросов без роста RSS.

| Параметр | Значение |
| --- | --- |
| Интенсивность | 10 000 rps |
| Длительность | Считается от интенсивности: `-Scenario soak` сам берёт `10 000 000 / rate` секунд |
| Трафик | `-BodyProfile mixed`, все флаворы, включая обрывы, таймауты и молчание |

```powershell
.\scripts\run.ps1 -Scenario soak -Rate 10000 -Edges 2 -Inspectors 4 `
                  -BodyProfile mixed -AbortRatio 0.05 -TimeoutRatio 0.02 `
                  -SilentRatio 0.01 -SlowRatio 0.02 -Obs
```

Ключ `-Duration` в этом сценарии игнорируется намеренно: критерий сформулирован в запросах, а не в
минутах, и длительность обязана следовать за интенсивностью, иначе прогон на сниженном rps молча
перестанет быть тем прогоном, которого требует критерий.

Смысл раскладки в том, чтобы прогон был неоднородным: утечка на редком пути исполнения при сплошных
GET не проявится. Обрывы, таймауты и молчание — как раз редкие пути, и доля в проценты набирает за
семнадцать минут сотни тысяч срабатываний.

**Критерии.**

- RSS снимается раз в 5 секунд в `stats.csv`; наклон линейной регрессии по второй половине прогона
  неотличим от нуля. Сравнение двух точек «до и после», как в
  tests/e2e (`docs/tests/e2e/README.md`), слишком грубо: оно не отличает утечку от
  однократного роста пулов на прогреве. Ряд идёт по контейнеру, а не по воркеру — утечка в одном
  воркере из четырёх на нём видна вчетверо слабее, и на семнадцати минутах это уже существенно.
- Число дескрипторов и число соединений стабильны.
- Добавленная задержка на p99 в последней минуте не хуже, чем в первой после прогрева.
- Прогон под ASan отдельно, на сниженной интенсивности — санитайзер меняет и скорость, и профиль
  памяти, поэтому критерий RSS к нему не применяется, применяется только отсутствие отчётов.

## reload-under-load

**Цель.** Критерий этапа 13: `reload` под десятью тысячами запросов в секунду не теряет запросы сверх
политики.

| Параметр | Значение |
| --- | --- |
| Интенсивность | 10 000 rps |
| `reload` | Каждые 30 секунд, 20 раз за прогон |
| Трафик | Доля медленных запросов обязательна: перезагружать нечего, если в момент `reload` никто не ждёт вердикта |

Перезагрузку скрипт прогона не делает — её нужно подать снаружи, из второго окна, пока идёт нагрузка:

```powershell
.\scripts\run.ps1 -Scenario steady -Rate 10000 -Duration 10m -SlowRatio 0.2 -Edges 2
```

```powershell
# во втором окне, в том же каталоге
1..20 | ForEach-Object {
    docker compose -f compose.load.yml exec -T edge nginx -s reload
    Start-Sleep -Seconds 30
}
```

С несколькими узлами `exec` попадёт в один из них; чтобы перезагружать все, нужен цикл по
`docker compose -f compose.load.yml ps -q edge`.

**Что ловит.** Дренаж завершающихся воркеров: запросы, ожидающие вердикт в старом воркере, должны
дождаться его или завершиться по политике, а не оборваться. Отдельно — начальное значение поколения
слотов: оно случайно в каждом воркере и в каждом поколении конфигурации именно затем, чтобы после
`reload` новый воркер не выдавал те же `rid`, что и завершающийся. Прогон с двадцатью перезагрузками
подряд — единственный способ это нагрузить.

**Критерии.**

- Оборванных соединений нет; допустимы только завершения по политике отказа.
- Всплеск задержки на `reload` не превышает `waf_deadline` и укладывается в одну секунду по времени.
- Число воркеров возвращается к штатному после каждой перезагрузки: залипший завершающийся воркер —
  это удержанный слот и утечка памяти.

## bus-only

**Цель.** Измерить шину и инспектор без nginx: модуль в этом сценарии не участвует, поэтому его
результат — эталон, а не измерение WAF.

На месте модуля — `ip-probe`: он собирает сообщение того же формата по
протоколу вердикта (`docs/verdict-protocol.md`), публикует его на subject инспектора со
своим инбоксом в `reply-to` и печатает вердикт.

```powershell
docker compose -f compose.load.yml exec inspector ip-probe --quiet --client-ip 8.8.8.8
docker compose -f compose.load.yml exec inspector ip-probe --quiet --client-ip 203.0.113.10 --expect deny
```

Это даёт RTT — эталон, с которым сравнивается латентность инспектора, снятая модулем через
`X-WAF-Debug`: разница между двумя числами и есть цена клиента в воркере.

Потолка по потоку он не даёт: запросы идут строго по одному, следующий отправляется после ответа на
предыдущий, так что `--count 20000` измерит те же 20 000 последовательных RTT, а не 20 000 сообщений
в секунду. Для потолка нужен либо параллельный режим в самом `probe`, либо `nats bench --reply` — но
второй меряет голую шину без разбора вердикта, а именно разбор и составляет заметную часть
стоимости. Строки про поток в таблице ниже поэтому пока не проверяются ничем.

| Параметр | Сейчас | Как задумано |
| --- | --- | --- |
| Поток | Последовательный, один в полёте | 4 000 / 20 000 / 60 000 сообщений в секунду, по [расчёту](README.md#нагрузка-на-шину) |
| В полёте | Один | Ограничение, эмулирующее `waf_max_inflight` |
| Инспектор | Один экземпляр, `queue subscribe` | То же |
| Размер сообщения | Умолчания `probe`, тело задаётся ключом `--body` | Из профиля `mixed`, без тела и с инлайновым телом |

**Что ловит.** RTT в отсутствие нагрузки от nginx — эталон, с которым сравнивается результат клиента
в воркере. Задуманное, но пока недостижимое: потолок единственного инспектора, стоимость разбора
JSON в нём и поведение шины при превышении `max_payload`.

**Критерии.**

- p99 RTT укладывается в единицы сотен микросекунд — формулировка критерия выхода этапа 2 из
  `docs/roadmap.md`. Единственный из перечисленных, который проверяется
  сегодня.
- Инспектор держит 20 000 сообщений в секунду без роста очереди и без роста RSS.
- Ни одного потерянного ответа: число ответов равно числу запросов.
- Сообщение сверх `max_payload` отвергается шиной с явной ошибкой, а не молча теряется.

## bus-fault

**Цель.** Проверить, что отказы шины дают документированное поведение.

Воздействия подаются снаружи, из второго окна, пока идёт нагрузка. Префикс `docker compose -f
compose.load.yml` опущен для краткости.

| Воздействие | Как | Ожидание |
| --- | --- | --- |
| Рестарт NATS | `restart nats` | Переподключение без потери висящих запросов сверх политики |
| Инспектор завис | `kill -s STOP inspector` | Поведение по `waf_exception <фаза> timeout`, затем открытие breaker: запросы к инспектору перестают публиковаться, а латентность возвращается к дедлайну без него |
| Инспектор снят | `stop inspector` | Поведение по `waf_exception <фаза> absent`, отличное от таймаута |
| Задержка сети | `tc netem delay 50ms` внутри контейнера NATS | Срабатывание `waf_deadline`, поведение по классу `timeout` |
| Потери | `tc netem loss 5%` там же | То же, без накопления запросов в полёте |

Оживить остановленный инспектор — `kill -s CONT inspector`. Два последних воздействия требуют
`NET_ADMIN` и самого `tc`, которых у контейнера NATS нет: понадобится либо `--cap-add`, либо
`nsenter` в его сетевое пространство с хоста; на Docker Desktop проще второе, через служебный
контейнер с `--network container:<id>`.

Различие второй и третьей строк существенно: отсутствие подписчиков на subject обнаруживается сразу,
а зависший инспектор — только по дедлайну. Классы `waf_exception` у них разные — `absent` и
`timeout`, — а умолчание у обоих одно, `deny`, поэтому по коду ответа они неразличимы. Задавать их
в прогоне нужно явно, ключом `-OnTimeout` и переменной `WAF_ON_ABSENT`, иначе прогон проверит
умолчание, а не исключение.

Ожидаемый код ответа генератор в этих прогонах вычислить не может: он знает задержку инспектора, но
не знает, что инспектора вынули. Поэтому `unexpected_status` здесь заведомо ненулевой и критерием не
является — смотреть надо на распределение кодов в статистике HAProxy
(`results/<прогон>/after/haproxy-stat.txt`) и на `error_log` узла.

**Критерии.**

- Каждое воздействие даёт ровно то поведение, которое предписано соответствующей директивой.
- После снятия воздействия система возвращается к штатным показателям без перезапуска.
- Число запросов в полёте не растёт монотонно ни при одном из воздействий: рост означает, что
  освобождение слота зависит от ответа, которого не будет.
